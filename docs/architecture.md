# Архитектура мультиплеера kinō

```
                 https://sohimazdai.ru/cine/?r=<комната>
 ┌──────────────┐  статика (Caddy, старый VPS 45.159.189.71, рядом с planner)
 │   Браузер    │◄────────────────────────────────────────────────────────────
 │ Three.js     │
 │ app.js       │  wss://api.sohimazdai.ru/ws   — состояние комнаты, позы, события
 │ net.js       │◄───────────────────────────────►┌──────────────────────────────┐
 │ media.js     │                                 │ новый VPS 185.209.162.2      │
 │              │  wss://api.sohimazdai.ru/rtc    │ Caddy :443 (TLS)             │
 │              │◄───────────────────────────────►│  /ws  → kino-sync :8090      │
 │              │  UDP 7882 / TCP 7881 / TURN 3478│  /rtc → LiveKit  :7880       │
 └──────────────┘◄───────────────────────────────►│ LiveKit SFU (медиа)          │
                                                  └──────────────────────────────┘
```

Два независимых канала:

- **Синхронизация** (`server/`, Node 22 + `ws`) — комнаты, присутствие, позы аватаров, броски и эмоции, стикеры, голоса, таймер, реквизит, физика кубиков и мяча.
- **Медиа** (LiveKit SFU) — микрофон, камеры, показ экрана. Сервер синхронизации выдаёт токен LiveKit при входе в комнату, поэтому отдельной авторизации нет.

## Как достигается минимальная задержка

| Решение | Почему |
|---|---|
| Свой аватар считается в браузере | Нажатие клавиши двигает персонажа в том же кадре, без ожидания сервера. Физика (`physics.js`) детерминирована и общая для всех. |
| Сервер пересылает позу сразу, без «тиков» | Нет ожидания следующего такта: пересылка внутри сервера занимает ~1 мс (замер на сервере: p50 0,8 мс, p99 1,4 мс; через Caddy+TLS p50 1,1 мс). |
| Позы до 30 в секунду, в покое — раз в секунду | Плавность при движении и почти нулевой трафик в покое. После остановки ещё 200 мс шлются одинаковые позы, чтобы у других персонаж встал точно. |
| Интерполяция снимков с адаптивной задержкой | Чужие аватары показываются чуть в прошлом (45–220 мс, по измеренному джиттеру), всегда между двумя реальными снимками — без рывков. При нехватке данных — короткая экстраполяция (до 120 мс). |
| Синхронизация часов по пингам (как NTP) | Позы и события помечены временем сервера; клиенты сопоставляют их с одинаковой шкалой. |
| События (бросок, пинок, эмоция) проигрываются в момент их позы | Снежок вылетает из руки там, где персонаж находится на экране зрителя. |
| Физика кубиков и мяча — на сервере, с предсказанием на клиенте | Пинок виден сразу (клиент применяет его локально), сервер подтверждает. Ответ сервера «доматывается» вперёд на измеренную задержку, а остаток ошибки плавно гасится за ~100 мс. Все видят одно и то же положение. |
| Без сжатия WebSocket, `TCP_NODELAY`, BBR + `fq`, `tcp_notsent_lowat` | Меньше буферизации и задержки на каждом сообщении. |
| Медиа через SFU по UDP | Каждый отправляет свой поток один раз, сервер раздаёт остальным; simulcast и dynacast экономят канал. |

Сервер и фронт стоят в одном дата-центре (Амстердам, задержка между ними 0,3 мс). Задержка пользователя ≈ половина его RTT до Амстердама в каждую сторону плюс буфер интерполяции.

## Актуальное состояние у всех

- Источник истины для общего состояния — сервер. Все изменения — операции (`note.add`, `note.vote`, `struct.move`, `timer.start` …), которые сервер проверяет и применяет функциями из `dist/state.js`, а затем рассылает результат всем.
- Те же функции работают в браузере, когда связи нет (`?api=off` или сервер недоступен): комната продолжает работать локально и кэшируется в `localStorage`.
- Новичок и переподключившийся получают полный снимок: участники, стикеры, таймер, положения и скорости всех кубиков и мяча.
- Перетаскивание стикеров и конструкций видно другим в реальном времени (до 20 обновлений в секунду), финальное положение отправляется при отпускании.
- Перетаскиваемый кубик или мяч «принадлежит» одному участнику, пока его держат; другие не могут перехватить.
- Голы засчитывает сервер и объявляет всем с именем забившего.
- Идентичность стабильна: один и тот же браузер в одной комнате всегда получает один и тот же id, поэтому переподключение и перезапуск сервера не рвут медиа-сессию. Вторая вкладка того же браузера вытесняет первую.

## Протокол (JSON поверх WebSocket)

Клиент → сервер: `hello {room, uid, profile, pose}` — первым сообщением; затем `pose`, `act {k: throw|kick|emote|jump}`, `profile`, `ping {c}` и операции состояния.

Сервер → клиент: `welcome {id, voter, s, you, peers, state, objs, rtc}`, `join`, `leave`, `pose {id, s, x, y, z, a, vy, g}`, `act`, `profile`, `note`, `note.move`, `note.del`, `cube`, `cube.del`, `objs {s, o:[[id,x,y,z,vx,vy,vz,spin,rot]…]}`, `struct`, `goal`, `timer`, `pong`, `error`.

## Хранение и ограничения

- Состояние комнаты: `/var/lib/retrocine/rooms/<id>.json`, запись через 2 с после изменения и при остановке службы. Комнаты, в которые не заходили 30 дней, удаляются.
- Комната выгружается из памяти через минуту после ухода последнего участника.
- До 16 участников в комнате (столько же в LiveKit), 80 стикеров, 24 кубика.
- Ограничение частоты сообщений на соединение, 40 соединений с одного IP, сообщения до 64 КБ, разрешённые Origin: `https://sohimazdai.ru` и localhost.
- `uid` браузера никогда не уходит другим участникам: голоса хранятся по производному `voter`, id участника тоже производный.

## Медиа (LiveKit)

- Сигналинг: `wss://api.sohimazdai.ru/rtc` (через Caddy), медиа: UDP 7882 (один порт на всё), запасной ICE/TCP 7881, встроенный TURN по UDP 3478 (релей 30000–30999).
- Камеры — 540p с simulcast (180p/360p), показ экрана — 1080p 15 к/с; эхо- и шумоподавление включены.
- Видео идёт в текстуры той же 3D-сцены: камера — в плитку участника, показ экрана — на всю стену.
- Ограничение: сети, где закрыт весь UDP и все порты кроме 443 (строгие корпоративные), сейчас не подключат медиа. Решение — TURN по TLS на 443 через отдельное имя (например, `turn.sohimazdai.ru`) и мультиплексирование по SNI. Синхронизация сцены в таких сетях работает (это обычный HTTPS/WebSocket).

## Файлы

| Где | Что |
|---|---|
| `dist/net.js` | Соединение, переподключение, часы сервера, буфер интерполяции поз |
| `dist/media.js` | LiveKit: подключение, публикация микрофона/камеры/экрана, видео в текстуры |
| `dist/state.js` | Общие операции над состоянием комнаты и шаг физики (сервер и офлайн-режим) |
| `dist/world.js` | Описание реквизита без Three.js: конструкции, коллайдеры, мяч, ворота |
| `dist/config.js` | Адрес сервера, комната из `?r=`, ссылка-приглашение |
| `server/src/` | `index.js` (HTTP, WebSocket, комнаты), `room.js` (комната, физика, рассылка), `store.js`, `livekit.js` |
| `server/test/` | Интеграционные тесты сервера с настоящими WebSocket-клиентами |
| `tests/scene.test.mjs` | Тесты фронта, включая мультиплеер на подставном сервере |
| `deploy/` | Установка серверов и выкладка, см. [servers.md](servers.md) |
